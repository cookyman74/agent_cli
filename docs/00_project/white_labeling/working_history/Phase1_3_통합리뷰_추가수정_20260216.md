### 2.1 Issue 1: link extension uninstall이 원본 소스 디렉토리 삭제

**문제**:

이전 수정(`758520b12`)에서 uninstall을 `extension.path` 직접 사용으로
변경했으나, link-type extension의 경우:

- `loadExtension(extensionDir)` → `installMetadata.type === 'link'` →
  `effectiveExtensionPath = installMetadata.source` (원본 소스)
- `extension.path = effectiveExtensionPath` (line 661)
- uninstall 시 `rm -rf extension.path` → **원본 소스 디렉토리 삭제**

**수정**:

```typescript
// extension-manager.ts — link-type 가드 추가
const pathToDelete =
  extension.installMetadata?.type === 'link'
    ? new ExtensionStorage(extension.name).getExtensionDir()
    : extension.path;
await fs.promises.rm(pathToDelete, { recursive: true, force: true });
```

- link-type: 메타데이터 디렉토리(`~/.didim/extensions/name/`) 삭제
- non-link: `extension.path`(= 설치 디렉토리) 삭제 (기존 동작 유지)

### 2.2 Issue 2: OAuth token clear/delete 시 legacy 토큰 부활

**문제**:

`deleteTokenFiles()`에서 `new Set([tokenWritePath, tokenReadPath])` 사용:

1. 양쪽 파일 존재 시 `tokenReadPath` = `.didim/...` (resolveReadPath 우선순위)
2. `tokenWritePath` = `.didim/...`
3. Set dedup → `{.didim/...}` 1개만 → `.gemini/...` 파일 미삭제
4. `.didim/...` 삭제 후 다음 read → `.gemini/...` 파일 발견 → **legacy 토큰
   부활**

**수정**:

```typescript
// file-token-storage.ts — 양쪽 경로 명시적 포함
const home = homedir();
const tokenFileName = 'mcp-oauth-tokens-v2.json';
for (const tokenPath of new Set([
  this.tokenWritePath,
  this.tokenReadPath,
  path.join(home, DIDIM_DIR, tokenFileName),
  path.join(home, LEGACY_GEMINI_DIR, tokenFileName),
])) {
  try {
    await fs.unlink(tokenPath);
  } catch (error: unknown) {
    if ((error as NodeJS.ErrnoException).code !== 'ENOENT') throw error;
  }
}
```

## 5. Lessons Learned

- **link-type extension.path 위험**: `extension.path`가 반드시 설치 디렉토리를
  가리키지 않음. link-type은 원본 소스 경로를 가리키므로
  `rm -rf extension.path`는 소스 파괴. `installMetadata.type` 가드 필수
- **Set dedup + dynamic resolve 함정**: `resolveReadPath` getter + Set dedup
  조합 시, 동적 resolve 결과가 현재 파일 시스템 상태에 의존하여 삭제 후 legacy
  파일이 부활. 삭제 작업은 양쪽 경로를 명시적으로 포함
- **빈 tempDir rollback**: 백업 없는 tempDir에서 rollback하면 빈 디렉토리로 복원
  = 사실상 삭제. 백업 → 작업 → 롤백 순서 필수
- **read vs write 경로 분리**: `resolveReadPath`는 읽기 전용(fallback 탐색).
  쓰기 작업에는 항상 write 전용 경로(`getGlobalWritePath` 등) 사용하여 legacy
  경로 기록 방지

### 7.1 Issue 6: MemoryTool 첫 저장 시 legacy 메모리 내용 유실

**문제**:

`memoryTool.ts`의 `performAddMemoryEntry()`가 write path(`~/.didim/AGENTS.md`)
에서만 읽기 시도. `.didim/AGENTS.md` 미존재 + `.gemini/AGENTS.md` 존재 시:

1. `readFile(memoryFilePath)` → ENOENT
2. `currentContent = ''` → **legacy 내용 유실**
3. 빈 내용에 새 메모리 추가 → 기존 메모리 전체 소실

**수정**:

```typescript
// memoryTool.ts — optional read path 파라미터 추가
static async performAddMemoryEntry(
  text: string,
  memoryFilePath: string,
  fsAdapter: { ... },
  memoryFileReadPath?: string, // ← 추가
): Promise<void> {
  let currentContent = '';
  try {
    currentContent = await fsAdapter.readFile(memoryFilePath, 'utf-8');
  } catch (_e) {
    // Write path 미존재 → legacy read path fallback
    if (memoryFileReadPath && memoryFileReadPath !== memoryFilePath) {
      try {
        currentContent = await fsAdapter.readFile(memoryFileReadPath, 'utf-8');
      } catch (_e2) { /* 양쪽 미존재 = 새 파일 */ }
    }
  }
  // ... write to memoryFilePath
}

// Call site: getGlobalMemoryFilePath() (resolveReadPath) 전달
await MemoryTool.performAddMemoryEntry(
  fact, getGlobalMemoryFileWritePath(), fsAdapter,
  getGlobalMemoryFilePath(), // ← read path 추가
);
```

- write path 파일 존재: 기존 동작 (write path에서 읽기)
- write path 미존재 + read path 존재: legacy 내용 보존 후 write path에 저장
- 양쪽 미존재: 빈 파일 생성 (기존 동작)

**파일**: `packages/core/src/tools/memoryTool.ts`

## 10. Lessons Learned (추가)

- **performAddMemoryEntry read/write 분리**: write path에서만 읽으면 legacy 내용
  유실. write path 미존재 시 read path(resolveReadPath)를 fallback으로 시도해야
  legacy→primary 마이그레이션 자연스럽게 수행
- **OAuth clear 양쪽 경로**: `resolveReadPath` 기반 read + 단일 write path 삭제
  조합은 삭제 후 legacy 부활. 삭제 작업은 반드시 양쪽 경로를 명시적으로 포함
- **mkdir 대칭성**: 동일 파일에 대한 write 경로를 사용하는 모든 메서드에서 mkdir
  호출 필수. 한 메서드에만 있고 다른 메서드에 없으면 legacy-only 상태에서 ENOENT
- **read/write path 분리 원칙**: `resolveReadPath`는 읽기 전용(fallback 탐색).
  `getEnvFilePath` vs `getEnvFileWritePath` 패턴으로 읽기/쓰기 경로를 명시적
  분리

### Issue 18: sensitive setting .env 평문 잔존
