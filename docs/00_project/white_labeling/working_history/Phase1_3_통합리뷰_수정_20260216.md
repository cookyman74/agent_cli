## 2. 수정 상세

### 2.1 Issue 1+6: Extension uninstall 경로 + `.env` 검색 경로

**문제**:

- `extension-manager.ts`: uninstall 시
  `new ExtensionStorage(name).getExtensionDir()` 사용 → resolver가 부모 디렉토리
  레벨에서 resolve하여 실제 설치 경로와 불일치
- `ExtensionStorage.getExtensionDir()`: `getUserExtensionsDir() + name` = 부모
  디렉토리 레벨 resolve → `.didim/extensions` 존재하면
  `.gemini/extensions/foo`의 `.env`를 찾지 못함

**수정**:

```typescript
// extension-manager.ts — extension.path 직접 사용
await fs.promises.rm(extension.path, { recursive: true, force: true });

// storage.ts — extension-specific 레벨 resolve
getExtensionDir(): string {
  return resolveReadPath(homedir(), 'extensions', this.extensionName);
}
```

### 2.3 Issue 5: FileTokenStorage read path 캐싱

**문제**: `tokenReadPath`가 `private readonly` 필드로 생성 시점에 캐시.
`setCredentials()` → `.didim/` 파일 생성 후에도 `getCredentials()`가 캐시된
`.gemini/` 경로에서 읽기 시도 → stale data. `clearAll()`은 `.didim/` 파일만 삭제
→ legacy 파일 잔존.

**수정**:

```typescript
// readonly 필드 → getter (동적 resolve)
private get tokenReadPath(): string {
  return resolveReadPath(homedir(), 'mcp-oauth-tokens-v2.json');
}

// 양쪽 경로 삭제 헬퍼
private async deleteTokenFiles(): Promise<void> {
  for (const tokenPath of new Set([this.tokenWritePath, this.tokenReadPath])) {
    try { await fs.unlink(tokenPath); }
    catch (error) { if ((error as NodeJS.ErrnoException).code !== 'ENOENT') throw error; }
  }
}
```

## 5. Lessons Learned

- **부모 디렉토리 레벨 resolve 위험**: `resolveReadPath(base, 'extensions')` +
  `path.join(result, name)`은 부모에서 `.didim`/`.gemini` 결정 후 자식 경로를
  추가하므로, `.didim/extensions` 존재하면 `.gemini/extensions/foo`를 찾지 못함
  → `resolveReadPath(base, 'extensions', name)`으로 extension-specific 레벨에서
  resolve 필수
- **readonly 필드 vs getter 패턴**: read path를 생성 시점에 캐시하면 write 후
  stale. 동적 resolve가 필요한 경로는 getter로 구현 → Set dedup으로 동일 경로
  중복 삭제 방지
- **auto-mock 주의**: `vi.mock('@didim365/agent-cli-core')`는 모든 export를
  `vi.fn()`으로 대체. `resolveReadPath` 같은 유틸 함수도 mock되어 `undefined`
  반환 → 테스트에서 구현 변경 시 mock 누락 주의
- **a2a-server 독립 경로 관리**: Core의 `Storage` 클래스를 사용하지 않으므로,
  Core에서 수정된 fallback 패턴이 자동 전파되지 않음 → 별도 검증 필수
