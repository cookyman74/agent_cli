## 1. 이슈 요약

### 증상

non-Gemini 프로바이더(Claude, OpenAI) 선택 시, **레거시 Gemini
API**(`generateContent`, `generateContentStream`, `countTokens`,
`embedContent`)를 직접 호출하는 모든 경로가 다음 에러로 실패:

```
Provider "claude" does not support legacy Gemini API. Use llm* methods.
```

### 영향 범위

메인 대화 루프(`client.ts:processTurn()`)만 `isProviderIndependentGenerator()`
체크 후 `llm*` 메서드 경로를 사용. **그 외 모든 내부 LLM 호출 경로**가 레거시
API에 의존.

| 카테고리            | 영향 경로                                                                   | 실패 방식        |
| ------------------- | --------------------------------------------------------------------------- | ---------------- |
| **A. 서브에이전트** | `LocalSubagentInvocation` → `GeminiChat.generateContentStream()`            | 스트리밍 실패    |
| **B. 유틸리티 LLM** | `BaseLlmClient._generateWithRetry()` → `contentGenerator.generateContent()` | 비스트리밍 실패  |
| **C. 도구 내 LLM**  | `GeminiClient.generateContent()` (web-fetch, web-search)                    | 비스트리밍 실패  |
| **D. 토큰 계산**    | `contentGenerator.countTokens()` (tokenCalculation)                         | 토큰 카운트 실패 |
| **E. 임베딩**       | `contentGenerator.embedContent()` (BaseLlmClient)                           | 임베딩 실패      |

### 메인 대화는 정상

```
client.ts processTurn()                     [client.ts:638-694]
  │  isProviderIndependentGenerator(generator) && isNonGemini 체크
  ▼
processLlmTurn()                            [client.ts:843-984]
  │  generator.llmGenerateContentStream()   ← 프로바이더 독립 메서드
  ▼
  ✅ 정상 동작
```

## 2. 근본 원인 분석

### 핵심 원인: `wrapAdapterAsGenerator()` 레거시 메서드 throw

`contentGenerator.ts:144-180`의 `wrapAdapterAsGenerator()`가 non-Gemini 어댑터를
`GeminiContentGenerator` 인터페이스로 래핑할 때, **레거시 메서드를 모두
throw하도록 구현**:

```typescript
// contentGenerator.ts:147-166
function wrapAdapterAsGenerator(adapter: BaseAdapter): GeminiContentGenerator {
  return {
    providerName: adapter.providerName,
    generateContent: () => { throw new Error(`Provider "${adapter.providerName}" does not support legacy Gemini API.`); },
    generateContentStream: () => { throw new Error(...); },
    countTokens: () => { throw new Error(...); },
    embedContent: () => { throw new Error(...); },
    // ✅ llm* 메서드만 실제 어댑터에 위임
    llmGenerateContent: (req, id, opts) => adapter.generateContent(req, id, opts),
    llmGenerateContentStream: (req, id, opts) => adapter.generateContentStream(req, id, opts),
    llmCountTokens: (req) => adapter.countTokens(req),
  };
}
```

메인 대화 루프만 `isProviderIndependentGenerator()` 타입 가드를 사용하여 `llm*`
경로로 분기. 나머지 모든 내부 호출은 레거시 메서드를 직접 사용.

## 5. 상세 설계

### 5.A 서브에이전트 스트리밍 경로

#### 5.A.1 신규 파일: `packages/core/src/agents/llmAgentChatSession.ts`

`AgentChatSession` 인터페이스를 구현하여 `llmGenerateContentStream()`을
사용하고, `LlmEvent` → `StreamEvent` 변환을 수행.

**클래스 설계**:

```typescript
export class LlmAgentChatSession implements AgentChatSession {
  private history: Content[];
  private lastPromptTokenCount: number = 0;

  constructor(
    private readonly config: Config,
    private readonly generator: ProviderIndependentGenerator,
    private readonly providerName: string,       // resolveProviderModel에 사용
    private readonly systemInstruction: string | undefined,
    private readonly tools: Tool[],
    initialHistory: Content[],
  )
}
```

> **[리뷰 반영 #1]** constructor에서 고정 `providerModel` 제거. 대신
> `providerName`만 저장하고, `sendMessageStream()` 호출 시
> `modelConfigKey.model`을 `resolveProviderModel()`로 매 턴마다 해석. 이는
> `local-executor.ts:660-695`의 per-turn 모델 라우팅(`getModelConfigAlias()` →
> `modelConfigService.getResolvedConfig()` → auto-routing)과 정합.

**`sendMessageStream()` 흐름**:

```
1. per-turn 모델 해석:
   resolvedModel = resolveProviderModel(modelConfigKey.model, this.providerName)

2. buildLlmRequestFromGeminiState({
     model: resolvedModel,             // ← 매 턴마다 새로 해석
     history: this.history,
     currentRequest: message,
     systemInstruction: this.systemInstruction,
     config: resolvedConfig.generateContentConfig,
     tools: this.tools,
   })

   // [2차 리뷰 반영 #1] tool_result role 후처리
   llmRequest.messages = fixToolResultRoles(llmRequest.messages)

3. this.history.push(userContent)      // streaming 전에 히스토리 추가

4. generator.llmGenerateContentStream(llmRequest, promptId, { signal })

5. for await (event of eventStream):
     accumulator.addEvent(event)

     // [리뷰 반영 #2] Error event → throw (not null)
     if (event.type === LlmEventType.Error) {
       throw event.error instanceof Error ? event.error : new Error(String(event.error));
     }

     // [리뷰 반영 #6 + 2차 리뷰 반영 #3] usage 추출 — MessageEnd OR Finished
     if (event.type === LlmEventType.MessageEnd && event.usage) {
       this.lastPromptTokenCount = event.usage.promptTokens;
     }
     if (event.type === LlmEventType.Finished && event.usage) {
       this.lastPromptTokenCount = event.usage.promptTokens;
     }

     streamEvent = convertLlmEventToStreamEvent(event)
     if (streamEvent) yield streamEvent    // local-executor로 전달

6. responseContent = accumulator.toContent()
   this.history.push(responseContent)
```

**`convertLlmEventToStreamEvent()` 변환 매핑**:

```typescript
function convertLlmEventToStreamEvent(event: LlmEvent): StreamEvent | null;
```

| LlmEvent          | → StreamEvent             | 변환 로직                                                                                                                                                                                                                         |
| ----------------- | ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `TextDelta`       | `CHUNK`                   | `{ candidates: [{ content: { role: 'model', parts: [{ text }] } }] }`                                                                                                                                                             |
| `ThoughtDelta`    | `CHUNK`                   | `{ candidates: [{ content: { role: 'model', parts: [{ text, thought: true }] } }] }`                                                                                                                                              |
| `ToolCallRequest` | `CHUNK`                   | candidates에 functionCall part + 최상위 `functionCalls` 배열                                                                                                                                                                      |
| `Retry`           | `RETRY`                   | 직접 매핑                                                                                                                                                                                                                         |
| `AgentStopped`    | `AGENT_EXECUTION_STOPPED` | `{ reason }`                                                                                                                                                                                                                      |
| `AgentBlocked`    | `AGENT_EXECUTION_BLOCKED` | `{ reason }`                                                                                                                                                                                                                      |
| `Error`           | _(throw)_                 | **[리뷰 반영 #2]** `throw event.error` — StreamEvent로 변환하지 않고 예외 전파. local-executor의 `callModel()` catch 블록에서 처리됨. Error를 null(skip)로 처리하면 `functionCalls.length === 0` → protocol_violation 오진단 발생 |
| `MessageEnd`      | `null` (skip)             | **[리뷰 반영 #6]** StreamEvent 불필요하지만, step 5에서 `lastPromptTokenCount` 업데이트 (OpenAI: usage 포함)                                                                                                                      |
| `Finished`        | `null` (skip)             | **[2차 리뷰 반영 #3]** Claude는 `Finished`에 usage 포함, `MessageEnd`에는 없음 → 양쪽 모두 체크                                                                                                                                   |
| 기타              | `null` (skip)             | accumulator에서 처리                                                                                                                                                                                                              |

> **[리뷰 반영 #2 상세]** `local-executor.ts:260-281`에서
> `functionCalls.length === 0`이면
> `AgentTerminateMode.ERROR_NO_COMPLETE_TASK_CALL` (protocol_violation)로 처리.
> LlmEventType.Error를 null로 skip하면 정상 응답이 없으므로 `functionCalls` 빈
> 배열 → protocol violation 오진단. throw하면 local-executor의 callModel()
> catch에서 정상 에러로 처리됨.

> **[리뷰 반영 #6 + 2차 리뷰 반영 #3 상세]** `AgentChatSession`
> 인터페이스(`agents/types.ts:46`)가 `getLastPromptTokenCount(): number` 요구.
> `chatCompressionService.ts:267`에서 `chat.getLastPromptTokenCount()`로 압축
> threshold 판단. 프로바이더별 usage 위치가 다름:
>
> - **OpenAI**: `MessageEnd`에 usage 포함 (`converter.ts:360`)
> - **Claude**: `Finished`에 usage 포함 (`converter.ts:512`), `MessageEnd`에는
>   usage 없음 (`converter.ts:528` — `{ type: LlmEventType.MessageEnd }` only)
>
> 따라서 **양쪽 이벤트 모두** usage 존재 시 `lastPromptTokenCount` 갱신.
> `Finished`가 `MessageEnd`보다 먼저 발행되므로 (Claude: message_delta →
> message_stop, OpenAI: finish_reason chunk → usage-only chunk), 마지막으로
> 갱신된 값이 최종값.

> **[2차 리뷰 반영 #1 상세]** `buildLlmRequestFromGeminiState()`
> (requestBuilder.ts:179)는 `convertContentsToLlmMessages()`만 호출하여
> tool_result role 교정이 없음. 서브에이전트 다중 턴에서 tool
> response(`local-executor.ts:1049` —
> `{ role: 'user', parts: [functionResponse] }`)가 히스토리에 쌓이면, 변환 후
> `{ role: 'user', content: [{ type: 'tool_result' }] }` → OpenAI converter가
> tool_result 누락. `fixToolResultRoles()`를 `buildLlmRequestFromGeminiState()`
> 결과의 `messages` 배열에 적용.

**모델 override**: `sendMessageStream(modelConfigKey, ...)` 호출 시
`modelConfigKey.model` (Gemini 모델명)을
`resolveProviderModel(modelConfigKey.model, this.providerName)`으로 해석하여
사용. `modelConfigService.getResolvedConfig()`의 `generateContentConfig`
(temperature, topP 등)는 유지.

**신규 private 메서드**: `_callLlmGenerateContent()`

```typescript
/**
 * Non-Gemini 프로바이더용 llmGenerateContent() 호출.
 * Content[] → LlmMessage[] 변환 후 llm* 메서드 사용,
 * 응답을 GenerateContentResponse 형태로 변환하여 반환.
 */
private async _callLlmGenerateContent(
  generator: ProviderIndependentGenerator,
  model: string,
  contents: Content[],
  systemInstruction: string | Part | Part[] | Content | undefined,
  generateContentConfig: GenerateContentConfig,
  additionalProperties?: { responseJsonSchema: Record<string, unknown>; responseMimeType: string },
  abortSignal?: AbortSignal,
  promptId?: string,
): Promise<GenerateContentResponse> {
  // 1. 모델명 해석
  const resolvedModel = resolveProviderModel(model, generator.providerName!);

  // 2. Content[] → LlmMessage[] 변환
  const rawMessages = convertContentsToLlmMessages(contents);

  // [리뷰 반영 #7] tool_result role 후처리
  const messages = fixToolResultRoles(rawMessages);

  // 3. systemInstruction 정규화
  const sysInstruction = typeof systemInstruction === 'string'
    ? systemInstruction
    : systemInstruction && 'text' in systemInstruction
      ? (systemInstruction as Part).text
      : undefined;

  // 4. LlmGenerateRequest 구성
  const request: LlmGenerateRequest = {
    model: resolvedModel,
    messages,
    systemInstruction: sysInstruction,
    temperature: generateContentConfig?.temperature ?? undefined,
    topP: generateContentConfig?.topP ?? undefined,
    maxTokens: generateContentConfig?.maxOutputTokens ?? undefined,
    // [리뷰 반영 #3] responseFormat은 'text' | 'json' 문자열 리터럴
    ...(additionalProperties && {
      responseFormat: 'json' as const,
    }),
  };

  // 5. llmGenerateContent() 호출
  const response = await generator.llmGenerateContent(
    request,
    promptId ?? 'baseLlmClient',
    { signal: abortSignal },
  );

  // 6. LlmGenerateResponse → GenerateContentResponse 변환
  return this._convertLlmResponseToGeminiResponse(response);
}
```

> **[리뷰 반영 #3]** `LlmResponseFormat`은 `'text' | 'json'` 문자열 리터럴

> `{ type: 'json_schema', jsonSchema: ... } as LlmResponseFormat`는 타입 오류.
> `additionalProperties`가 존재하면 `responseFormat: 'json'`으로 단순 설정. JSON
> Schema 기반 structured output은 별도 이슈로 관리.
>
> **[리뷰 반영 #7]** Gemini의 `functionResponse` part는 `role: 'user'`로

**신규 private 메서드**: `_convertLlmResponseToGeminiResponse()`

```typescript
/**
 * LlmGenerateResponse를 GenerateContentResponse 호환 형태로 변환.
 * BaseLlmClient 호출자들이 접근하는 필드만 채움:
 * - candidates[0].content.parts[0].text (getResponseText 호환)
 * - 기타 메타데이터는 빈 값
 */
private _convertLlmResponseToGeminiResponse(
  response: LlmGenerateResponse,  // [리뷰 반영 #4] LlmResponse → LlmGenerateResponse
): GenerateContentResponse {
  const textParts = response.content
    .filter((c) => c.type === 'text')
    .map((c) => ({ text: c.text }));

  return {
    candidates: [{
      content: {
        role: 'model',
        parts: textParts.length > 0 ? textParts : [{ text: '' }],
      },
    }],
  } as GenerateContentResponse;
}
```

> NOT `LlmResponse`. 구조:

#### 5.B.1 신규 유틸리티: `fixToolResultRoles()`

> **[리뷰 반영 #7]** Gemini ↔ non-Gemini 간 role 매핑 불일치 해결

**문제**: Gemini SDK의 `Content`에서 `role: 'user'`는 사용자 메시지와 tool
response(functionResponse part) 양쪽에 사용됨.
`convertContentsToLlmMessages()`(typeConversion.ts:123)는 이를 그대로
`{ role: 'user', content: [{ type: 'tool_result', ... }] }`로 변환. 그러나
OpenAI/Claude 컨버터는 `role: 'user'` 메시지에서 tool_result content를 인식하지
못함:

```
Gemini Content:    { role: 'user', parts: [{ functionResponse: { name, response, id } }] }
  ↓ convertContentsToLlmMessages()
LlmMessage:        { role: 'user', content: [{ type: 'tool_result', toolCallId, name, content }] }
  ↓ OpenAI convertUserMessage() → toOpenAiContentParts()
OpenAI message:    { role: 'user', content: [] }  ← tool_result 누락!
```

**해결**: `convertContentsToLlmMessages()` 결과에 후처리를 적용.
`role: 'user'`인 메시지의 content가 **모두** tool_result인 경우 `role: 'tool'`로
변경.

**위치**: `packages/core/src/core/llmMessageUtils.ts` (신규)

```typescript
import type { LlmMessage, LlmToolResultContent } from '../providers/types.js';

/**
 * Gemini Content[] → LlmMessage[] 변환 후 tool_result role 교정.
 *
 * Gemini는 functionResponse를 role:'user'로 포함하지만,
 * OpenAI/Claude 컨버터는 role:'user' 메시지에서 tool_result를 인식하지 못함.
 * tool_result-only user 메시지의 role을 'tool'로 변경.
 *
 * [2차 리뷰 반영 #4] 빈 toolCallId 가드: functionResponse.id가 없으면
 * toolCallId: '' 으로 변환됨(typeConversion.ts:53). OpenAI API는 빈
 * tool_call_id를 거부하므로, 모든 tool_result가 유효한(non-empty)
 * toolCallId를 가진 경우에만 role을 변경.
 */
export function fixToolResultRoles(messages: LlmMessage[]): LlmMessage[] {
  return messages.map((msg) => {
    if (msg.role !== 'user' || msg.content.length === 0) {
      return msg;
    }
    const allToolResult = msg.content.every((c) => c.type === 'tool_result');
    if (!allToolResult) {
      return msg;
    }
    // [2차 리뷰 반영 #4] 빈 toolCallId가 있으면 role 변경하지 않음
    // → API hard error보다 데이터 누락이 더 안전한 실패 모드
    const allHaveCallId = msg.content
      .filter((c): c is LlmToolResultContent => c.type === 'tool_result')
      .every((c) => c.toolCallId && c.toolCallId.length > 0);
    if (!allHaveCallId) {
      return msg;
    }
    return { ...msg, role: 'tool' };
  });
}
```

## 12. FAQ

### Q: `wrapAdapterAsGenerator()`의 레거시 메서드를 throw 대신 llm\* 브릿지로 변경하면 안 되나?

A: 가능하지만 권장하지 않음. 이유:

1. `generateContent()`의 입력(`GenerateContentParameters`)과
   출력(`GenerateContentResponse`)이 Gemini SDK 타입으로, 완벽한 양방향 변환이
   복잡
2. 모든 레거시 호출자가 암묵적으로 non-Gemini를 지원하게 되어, **의도하지 않은
   경로에서 non-Gemini 호출** 발생 가능
3. 호출자 쪽에서 명시적으로 분기하는 것이 디버깅/추적에 유리

### Q: BaseLlmClient의 Content[] → LlmMessage[] 왕복 변환이 비효율적이지 않나?

A: 맞지만, 유틸리티 호출은 빈도가 낮고(루프 감지, 압축 등 세션당 수 회), 변환
오버헤드는 API 호출 대비 무시할 수준. **호출자 코드 변경 0건**이라는 이점이 더
큼.

### Q: web-fetch의 `groundingMetadata`는 non-Gemini에서 어떻게 되나?

A: `web-search.ts`에서 `groundingMetadata`를 읽는데, 이는 Gemini의 Google Search
grounding 전용 기능. non-Gemini 응답에서는 항상 `undefined`로 반환되어 검색 결과
소스가 누락됨. 이는 별도 이슈로 관리 (현재 hotfix 범위 밖).
